2. Project Overview & Motivation

What it is about: each team chooses (or proposes) a real-world system such as a library, a hospital or a bank, and builds a desktop application that models it using well-designed classes and a graphical interface.

Why it matters: almost all professional software is built from objects that hide their data, share behaviour through hierarchies and can be extended without rewriting existing code. Learning to model a problem as objects is the most transferable skill in this course, and working in a large team mirrors real software projects.

Connection to OOP concepts (the four graded concepts):

  • Encapsulation: private fields, public getters/setters with validation, and no direct access to internal state.
  • Inheritance: a base class and at least two levels of specialised subclasses that reuse and extend behaviour.
  • Abstraction: abstract classes and/or interfaces that define what an object does while hiding how it does it.
  • Polymorphism: overriding methods and calling them through base-class references so that one call behaves differently per object type (plus overloading where useful).

3. Learning Objectives

By the end of the project you will be able to:

  • Analyse a problem statement and identify classes, attributes, behaviours and relationships.
  • Apply encapsulation to protect object state and validate data.
  • Build an inheritance hierarchy that avoids duplicated code.
  • Use abstraction (abstract classes and interfaces) to separate specification from implementation.
  • Demonstrate polymorphism through overriding and base-type references.
  • Draw UML class diagrams that match your implementation.
  • Connect a graphical interface to an object model.
  • Work in a team using version control, defined roles and a shared design.

7. Technical Requirements

Mandatory: language to be confirmed by the instructor (Java, C++, C# or Python).
  • Encapsulation: all attributes private/protected, accessed through methods that validate input.
  • Inheritance: at least one hierarchy with a base class and two or more subclasses (ideally two levels).
  • Abstraction: at least one abstract class and/or interface with abstract methods implemented by subclasses.
  • Polymorphism: overridden methods called through base-class or interface references, demonstrated visibly in the GUI.
  • Meaningful class, method and variable names, with comments or Javadoc (or equivalent) on every class and public method.
  • The code must compile and run without errors, and include a README with build and run instructions.
Important: design patterns (Factory, Singleton, Observer, Strategy, etc.) are not required and will not earn marks. Focus on clean use of the four concepts above.

The ZIP must contain: all source files, a README with build/run instructions, UML diagrams, sample data (if any) and a CONTRIBUTIONS.md file listing what each member did.

10. UML & Design Documentation

A UML class diagram is required: it must show all classes, attributes, methods, access modifiers, inheritance, interfaces/abstract classes and associations. A use-case or sequence diagram is optional but encouraged. The diagrams must be included in both the presentation and the code ZIP and must match the final code.
